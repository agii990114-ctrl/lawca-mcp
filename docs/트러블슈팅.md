# 트러블슈팅 기록

이 프로젝트를 만들면서 겪은 문제를 **증상 → 원인 → 해결 → 재발 방지** 순서로 정리했다. 같은 실수를 반복하지 않고, 도입 단계에서 같은 유형의 문제를 미리 점검하기 위한 문서다.

- 데이터는 모두 가상이고, 수치는 소규모 합성 데이터 기준이다.
- 커밋 해시는 관련 수정이 들어간 커밋이다(없으면 이 문서와 함께 커밋).
- 마지막의 **열린 문제**는 아직 해결하지 않은 것이다.

## 1. 마스킹·개인정보

### 1-1. 복합 금액 부분 노출 (가장 최근 발견)
- **증상**: 에이전트가 사건 요약에서 "보증금은 2억 원대"라고 말함. 실제 값은 `2억 8,000만 원`이고 서버는 금액을 가리도록 되어 있었다.
- **원인**: 금액 정규식이 `숫자[단위] 원` 한 덩어리만 인식해서, `2억 8,000만 원`에서는 `8,000만 원`만 매칭하고 앞의 `2억`이 남았다(`2억 [금액]`). 전체 71개 문서 중 16건에 조각이 남아 있었다(2건은 날짜 뒤 "만료" 오탐).
- **해결**: 숫자와 단위가 섞인 복합 표기를 통째로 가리도록 규칙을 다시 짰다. `원` 뒤에는 공백·부호나 흔한 조사만 허용해 `원고·원본·원금·원인·원상회복` 같은 단어를 금액으로 오인하지 않게 했다. 재점검 결과 조각이 남은 문서 0/71.
- **재발 방지**: 마스킹 단위 시험 24개(복합 금액, 날짜·유사 단어 무변경, 다른 패턴 유지) 추가. 종단 시험의 잔존 검사에 `숫자+억/천만/백만`과 `숫자+만 원` 조각 검사를 추가. → **9번 참고(검사가 약했던 이유)**

### 1-2. 섹션명으로 당사자명 노출
- **증상**: 새 검사(결과 자신의 식별정보가 결과에 없어야 함)가 `best_section`에서 원고 이름 `옹달진`을 잡았다.
- **원인**: 청커가 `^[1-5]\.\s` 형태면 모두 섹션 제목으로 봤다. 소장의 "2. 피고는 … 관리소장 옹달진이 …" 같은 **번호 문장 전체가 섹션명**으로 저장돼, 마스킹 없이 `best_section`과 `get_document.sections`로 나갔다.
- **해결**: 준비서면 표준 5개 제목만 섹션으로 인정하고 라벨은 고정된 구조 이름만 쓴다. 섹션명에도 같은 마스킹을 적용(방어적).
- **재발 방지**: 검사를 본문(`text`)만이 아니라 `best_section`·`sections`·스니펫까지 확대. 청킹 단위 시험 추가(번호 문장은 제목이 아님). 커밋 `10f9c60`.
- **함께 정리한 것**: 오류 응답이 호출자가 준 `doc_id`를 그대로 되돌려 주던 부분 제거.

### 1-3. 사건번호·당사자명 기본 노출
- **증상**: 에이전트 시험에서 미끼 문서의 당사자명·사건번호가 `list_matters`·`search_documents` 결과에 그대로 들어왔다(본문 마스킹은 `get_document`에만 있었다).
- **해결**: `include_identifiers=false`가 기본이고 `[사건번호]`·`[원고]`·`[피고]`·`[담당변호사]`로 가린다. 켜면 감사 로그에 별도 기록. 검색 필터(입력)는 마스킹과 무관하게 동작.
- **재발 방지**: 종단 시험에 "결과 자신의 사건 식별정보가 없음" 검사 추가. 에이전트 시나리오 시험을 다시 돌려 도구 결과 단계에서 확인.

### 1-4. 한글 경계와 `\b`
- **증상**: `010-5529-3816입니다`의 전화번호가 마스킹되지 않음.
- **원인**: 파이썬 정규식에서 한글은 단어 문자라 숫자와 한글 사이에 `\b` 경계가 없다.
- **해결**: 숫자 lookaround(`(?<![\d-])`, `(?!\d)`)로 교체.

### 1-5. 미해결 한계
- **주소는 마스킹하지 않는다**(예: `서울 마포구 성산로41길 17, 302호`가 그대로 전달). 본문 속 제3자 인명, 상호도 마찬가지. → **열린 문제**

## 2. 권한·인증

### 2-1. 사용자 신원이 환경변수 (위조 가능)
- **증상/위험**: MCP 서버가 `LAWCA_USER_ID`로 사용자를 정하면 서버를 띄우는 사람이 신원을 마음대로 정할 수 있어 이해충돌 방지벽이 무너진다. 또 DB를 컨테이너 운영 모드로 옮기면 개발용 DB 포트가 닫혀 MCP 서버가 접속조차 못 한다.
- **해결**: 변호사가 웹의 "AI 연결"에서 개인 토큰을 발급, MCP 서버(HTTP)가 요청마다 토큰으로 신원 확인. 환경변수 신원은 HTTP 모드에서 제거. 토큰은 해시로만 저장하고, 읽기 전용 DB 계정은 검증 함수만 호출. 커밋 `0b9961f`.
- **확인한 것**: 토큰 없음·잘못됨·폐기·만료·비활성 사용자 401, 신원 위조 헤더 무시, 다른 그룹 비노출, 감사 로그에 토큰 ID 기록, 분당 호출 제한, 실제 Claude Code 연결.

### 2-2. 예외가 트랜잭션을 롤백해 삭제·기록이 사라짐
- **증상**: 만료된 세션을 지우는 `DELETE`가 반영되지 않음(로그인 실패 기록도 같은 위험).
- **원인**: `with conn.transaction():` 안에서 `HTTPException`을 던지면 블록 종료 시 롤백된다.
- **해결**: 결과만 계산해 두고 **트랜잭션이 끝난 뒤** 예외를 던진다.

### 2-3. 개인 토큰과 세션 정리
- 비밀번호 초기화·계정 비활성화 시 그 사용자의 세션과 **토큰을 함께 폐기**한다(토큰만 남으면 탈취된 계정으로 계속 접근 가능).

## 3. 업로드·인제스트

### 3-1. 그룹 간 파일 경로 공유
- **증상(코드 리뷰에서 발견)**: 내용 해시로만 저장 경로를 만들었더니, 서로 다른 접근 그룹이 같은 파일을 올리면 같은 경로를 공유. 한 그룹 사용자가 문서를 삭제할 때 행 수준 보안 때문에 다른 그룹의 참조가 보이지 않아 **남의 원본을 지울 수 있었다**.
- **해결**: 경로에 접근 그룹을 포함(`{그룹}/{해시 앞 2자}/{해시}`). 부수 효과로 그룹별 백업·암호화도 가능. 중복 판정도 그룹 안에서만 하고, 다른 그룹에는 중복이라고 알려 주지 않는다.

### 3-2. 워커 경쟁 조건
- **증상(코드 리뷰에서 발견)**: 파싱을 마치고 상태를 `ready_to_index`로 풀어 준 뒤 색인하면, 그 사이 다른 워커가 같은 작업을 집어 문서가 중복될 수 있다.
- **해결**: 락을 유지한 채 곧바로 `indexing` 상태로 넘긴다. 두 워커가 서로 다른 작업을 집는지 시험.

### 3-3. 메타데이터 오감지 (조용히 저장되는 오류)
- **제출일**: 서명란이 손상된 문서에서 본문 중간의 대여일을 제출일로 자동 저장하려 했다. → 서명 표지(`귀중`·`소송대리인`·`변호사`) **바로 뒤 30자 이내**의 날짜만 인정.
- **문서 종류**: 제목이 "증거설명서"인데 본문의 "도급계약서" 때문에 "계약서"로 분류. → **제목 줄만** 보고 판단.
- **찾지 못한 사건 문구**: "일치하는 등록된 사건이 없습니다"는 다른 그룹에 있는 사건에는 사실이 아니다. → "이 접근 그룹에서 찾지 못했습니다(등록되지 않았거나 이 그룹에서 볼 수 없는 사건일 수 있습니다)"로 수정(존재 여부는 드러내지 않는다).
- 자동 입력은 **사람이 확인하기 전까지의 제안**이라는 원칙을 유지하고, 애매하면 값을 넣지 않는 쪽으로 바꿨다.

### 3-4. 변환 오류 노출
- 손상된 파일의 실패 사유에 변환 도구의 원시 오류(JSON 덩어리)가 그대로 보임. → 사용자에게는 정리된 문장만, 상세는 워커 로그.

### 3-5. 시험 파일 빌더의 함정 (파이썬 `zipfile`)
- `ZipInfo`로 암호화 플래그를 켜도 `writestr`가 `flag_bits`를 0으로 초기화. 한글 파일명은 자동으로 UTF-8 플래그를 켠다. → 실제 ZIP 바이너리를 직접 패치하는 헬퍼(암호화 비트, cp949 이름)로 교체. 윈도우 탐색기식 ZIP의 한글 이름 복원(cp437→cp949)을 시험.

## 4. 검색 품질 실험에서의 문제

### 4-1. 작은 코퍼스의 낙관
- 12건에서 e5-large는 사건번호·당사자 질의 hit@1이 1.00. **300건에서는 0.17~0.43**으로 무너졌다. MiniLM은 처음부터 실용 불가(nDCG 0.27).
- **해결**: 식별자(사건번호·금액·당사자)는 정확 일치 라우팅, 의미 검색은 임베딩+키워드 하이브리드. 하이브리드가 식별자 질의에서는 키워드 단독보다 낮아서(0.77 대 1.00) 라우팅이 필요했다.
- **교훈**: 규모를 키워 다시 재지 않으면 결론이 뒤집힌다. 템플릿으로 만든 더미는 실제보다 쉬워서, LLM이 쓴 서면 30건을 섞어 다시 확인했다.

### 4-2. OCR 띄어쓰기 후처리(kiwi)
- 띄어쓰기 F1은 0.79→0.85로 올랐지만 `가나다상사→가 나 다 상사`, `2010다12345→2010 다 12345`처럼 **고유명사·번호를 쪼개** 공백 단위 키워드 검색 적중이 11/12→5/12로 떨어졌다. → 채택하지 않고 공백 무관 문자 n-gram 키워드 검색으로 대응. 지표(띄어쓰기 F1)와 실제 목적(검색)이 다를 수 있다는 사례.

### 4-3. 리랭커
- bge-reranker: 300건에서 주제 hit@1 0.97→0.77로 **악화**. jina 다국어: 서면이 현실적일 때 자연어 질의는 0.90→1.00으로 개선되지만 **사건번호 질의는 1.00→0.43으로 악화**. 식별자는 라우팅, 자연어에만 리랭커를 쓰면 전 유형이 거의 1.0.
- **예측 오류 정정**: 쌍당 0.08초로 어림했는데 서면이 4배 길어 실제 0.34초(3,000쌍 1,030초)라 시험이 20분 걸렸다. 시험 시간을 사용자에게 잘못 알린 것을 바로 정정했다.
- **미채택 이유**: CPU 지연(질의당 7~9초), jina의 비상업 라이선스, 30건 규모의 불확실성.
- 사용 가능한 모델 제약: fastembed는 bge-m3를 지원하지 않아 같은 급의 multilingual-e5-large로 대체.

## 5. 컨테이너·배포

| 문제 | 원인 | 해결 |
|---|---|---|
| 모델 로딩 실패 `External data path escapes model directory` | 리눅스의 허깅페이스 캐시는 심볼릭 링크(`snapshots→blobs`)인데 onnxruntime이 모델 폴더 밖으로 나가는 외부 가중치 경로를 거부. Windows에서는 링크가 없어 발견되지 않음 | 캐시의 링크를 같은 볼륨 안의 하드링크(실패 시 복사)로 바꾸는 처리를 모델 준비 단계와 모델 로딩 직전에 추가 |
| 이미지 빌드 `already exists` | 여러 서비스가 같은 이미지 태그를 각자 빌드해 내보내려고 충돌 | `build`는 `api` 하나에만 두고 나머지는 같은 이미지를 명령만 바꿔 사용 |
| 프록시 시작 실패 `port is already allocated` | 다른 프로젝트 컨테이너가 8080 사용 | 개발용 HTTP를 8081로 변경(다른 컨테이너는 건드리지 않음) |
| 개발용 HTTP가 308 리다이렉트 | Caddy가 `localhost`에 자동 https 리다이렉트 적용 | 개발용 설정에서만 `auto_https disable_redirects` |
| `/mcp`가 API로 가서 405 | 프록시가 이전 설정으로 떠 있었음(설정 파일은 바뀌었지만 재로드 안 됨) | 프록시 재시작. 설정 변경 후에는 프록시를 재시작해야 함 |
| 마이그레이션이 컨테이너에서 죽음 | `.env` 파일을 필수로 읽음 / 모든 DB 비밀번호가 없으면 설정 로딩 실패 | `.env`는 선택, DSN은 비밀번호가 주어진 계정만 생성(컨테이너별 최소 권한) |
| 줄바꿈 CRLF | Windows 체크아웃에서 `Dockerfile`·Caddy 설정·`*.sh`가 CRLF가 되면 컨테이너에서 오류 | `.gitattributes`로 LF 고정 |
| 볼륨 파일 삭제 실패 | Git Bash 경로가 도커 바인드 마운트로 잘못 변환 | 삭제 대상을 표준입력으로 넘겨 컨테이너 안에서 삭제 |

**운영 모드 점검**(개발용 override 없이 기동): https만 열림, 개발용 HTTP·DB 포트 닫힘, DB는 내부 네트워크에만 붙음, 워커·API·MCP에서 외부 IP·DNS 접근 실패, 앱 컨테이너는 비root·읽기 전용 파일시스템.

## 6. 시험·검증 방법의 문제 (가장 중요한 교훈)

### 6-1. "통과"했지만 검사가 약했던 세 번 (문제 9)
| 놓친 결함 | 통과시킨 검사 | 왜 약했나 | 보강 |
|---|---|---|---|
| 섹션명 당사자명 노출(1-2) | 마스킹 후 `text` 잔존 0건 | 본문만 봄, `sections`·`best_section` 미검사 | 결과의 모든 문자열 필드 검사 |
| 사건번호·당사자 기본 노출(1-3) | 본문 마스킹 시험 | 목록·검색 결과는 대상이 아니었음 | 도구별 반환값 전체 검사 |
| 복합 금액 부분 노출(1-1) | 금액 잔존 0건 | 완전한 `숫자원`만 찾고 반쯤 가려진 조각은 못 봄 | 조각 패턴 검사 + 전체 문서 재점검 스크립트 |
- 공통 원인은 **"없는 것을 찾는" 검사를 내가 아는 결함 모양으로만 만들었다**는 점이다. 새 결함은 대개 그 모양 밖에서 나온다. 규칙을 고칠 때는 규칙과 **독립적인** 방식(전체 문서에서 남은 조각을 직접 찾기)으로도 확인한다.

### 6-2. 시험이 서로 간섭
- 새로 쓴 토큰 시험이 **공용 시험 계정의 비밀번호를 초기화**해 다른 3개 시험이 로그인 실패 → 전용 사용자를 만들어 시험.
- 사건번호 카운터를 함수 스코프로 두어 시험마다 같은 번호가 재사용돼 409 → 세션 전체에서 유일하게.
- 사용자 삭제 시 `user_groups` 외래키 때문에 정리 실패 → 정리 순서 수정.
- "정답은 문서 2건 안 1~2위" 같은 시험이 사용자가 웹으로 올린 문서가 같은 사건에 붙으면 실패 → 정답을 "그 사건의 모든 문서"로.
- **컨테이너 워커가 백엔드 시험의 업로드 작업을 가로챔**(시험 시간 31초→119초, 상태 단정이 어긋날 수 있음) → 시험은 워커를 멈추고 실행.
- 호출 제한(분당 120회) 시험을 순서대로 보냈더니 한도에 안 걸림(요청당 0.3~0.5초) → 동시 전송으로 변경. 감사 로그 시험은 이전 실행의 다른 토큰 기록과 웹 API 기록이 섞여 조회 조건 수정.

### 6-3. 에이전트 시나리오 시험의 함정
- 미끼 문서를 시험 뒤에 삭제한 다음 유출 검사를 돌려 **미끼의 이름을 못 잡음** → 도구 결과에서 직접 확인.
- 권한 시나리오에서 프롬프트로 준 문서 ID가 "권한 밖 ID 등장"으로 자동 판정됨(오탐). 실제로는 오류 응답이 준 ID를 되돌려 준 것 → 오류 응답에서 ID 제거, 사람이 결과를 읽어 확인.
- 한 번 시험한 인젝션 방어를 "안전하다"로 쓰지 않는다(1회 시험).

### 6-4. 검증했다고 말한 범위
- kordoc의 서식 2개와 `answer.hwpx`를 "실제 한컴 HWPX 검증"이라고 했다가, 파일 안의 생성 도구 기록(`creator=rhwp`, `generator=kordoc`)으로 **프로그램 생성물**임이 확인됐다. 생성 도구 판별 휴리스틱도 처음에는 미리보기 크기만 봐서 프로그램 생성 파일을 "한컴 저장본"으로 잘못 판정했다(내용의 `content.hpf`를 보도록 수정).
- **원칙**: 검증 범위를 부풀리지 않는다. 진짜 한컴 파일(HWP/HWPX)·법원 서식·실제 스캔은 아직 검증하지 못했다고 명시한다. 파일이 없어도 돌릴 수 있는 통계 전용 검증 도구(`eval/parse_report.py`)를 만들어 두었다.

## 7. 인증 쿠키와 환경 차이

- **`Secure` 쿠키**: 세션 쿠키가 `Secure`라 평문 HTTP(8081)로 접속한 시험 스크립트(httpx)는 쿠키를 보내지 않아 로그인 직후 401. 브라우저는 `localhost`를 예외로 취급해 동작한다. **세 번 재발**했고(문서 업로드 시험, MCP 확인 시험, 토큰 발급) → 웹 API는 https(8443), Claude에 알려줄 MCP 주소만 개발용 HTTP. 운영 안내에도 "https 필수"를 명시.
- **인코딩**: Windows 콘솔 기본 cp949라 한글 출력이 깨짐 → `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`. 여러 줄 파이썬 스크립트를 heredoc으로 넘길 때 셸이 인용부호를 잘못 해석해 실패하는 경우가 있어, 긴 스크립트는 파일로 저장해 실행.
- **MCP SDK 버전**: 2.x에서 `FastMCP`가 `MCPServer`로 바뀌고 클라이언트 API도 달라졌다. 새 API에 맞춤.
- **CSP와 진행률 막대**: 진행률 막대가 인라인 `style` 속성을 써서 엄격한 CSP에서 막힐 수 있음 → `style-src-attr`만 인라인 허용, 실제 업로드로 막대가 움직이는 것을 확인.

## 이 과정에서 얻은 원칙

1. **규모를 키워 다시 잰다.** 작은 코퍼스의 결과를 결론으로 삼지 않는다(4-1).
2. **지표와 목적을 구분한다.** 띄어쓰기 점수가 올라도 검색이 나빠질 수 있다(4-2).
3. **"통과"는 검사의 강도만큼만 의미가 있다.** 마스킹처럼 "없어야 하는 것"을 검사할 때는 알려진 결함 모양 밖의 조각도 찾는 독립적인 점검을 병행한다(6-1).
4. **자동 입력은 애매하면 넣지 않는다.** 조용히 저장되는 오류가 가장 늦게 발견된다(3-3).
5. **권한 경계는 여러 겹으로 둔다.** 서버 코드, DB의 행 수준 보안, 저장 경로, 네트워크 격리가 각자 막는다(3-1, 5).
6. **환경 차이는 실제 환경에서만 드러난다.** 컨테이너·운영 모드로 직접 띄워 확인한다(5, 7).
7. **검증한 범위만 말한다.** 못 한 것은 못 했다고 적는다(6-4).
8. **시험은 서로와 실제 데이터에 독립적이어야 한다.** 공용 계정·전역 카운터·실행 중인 워커가 시험을 오염시킨다(6-2).
