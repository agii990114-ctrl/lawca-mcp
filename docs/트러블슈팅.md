# 트러블슈팅 기록

이 프로젝트를 만들면서 겪은 문제를 **증상 → 원인 → 해결 → 재발 방지** 순서로 정리했다. 같은 실수를 반복하지 않고, 도입 단계에서 같은 유형의 문제를 미리 점검하기 위한 문서다.

- 데이터는 모두 가상이고, 수치는 소규모 합성 데이터 기준이다.
- 커밋 해시는 관련 수정이 들어간 커밋이다(없으면 이 문서와 함께 커밋).
- 마지막의 **열린 문제**는 아직 해결하지 않은 것이다.

## 1. 마스킹·개인정보

### 1-1. 복합 금액 부분 노출 (가장 최근 발견)
- **증상**: 에이전트가 사건 요약에서 "보증금은 2억 원대"라고 말함. 실제 값은 `2억 8,000만 원`이고 서버는 금액을 가리도록 되어 있었다.
- **원인**: 금액 정규식이 `숫자[단위] 원` 한 덩어리만 인식해서, `2억 8,000만 원`에서는 `8,000만 원`만 매칭하고 앞의 `2억`이 남았다(`2억 [금액]`). 전체 71개 문서 중 16건에 조각이 남아 있었다(2건은 날짜 뒤 "만료" 오탐).
- **해결**: 숫자와 단위가 섞인 복합 표기를 통째로 가리도록 규칙을 다시 짰다. `원` 뒤에는 공백·부호나 흔한 조사만 허용해 `원고·원본·원금·원인·원상회복` 같은 단어를 금액으로 오인하지 않게 했다. 재점검 결과 조각이 남은 문서 0/71.
- **재발 방지**: 마스킹 단위 시험 24개(복합 금액, 날짜·유사 단어 무변경, 다른 패턴 유지) 추가. 종단 시험의 잔존 검사에 `숫자+억/천만/백만`과 `숫자+만 원` 조각 검사를 추가. → **9번 참고(검사가 약했던 이유)**

### 1-2. 섹션명으로 당사자명 노출
- **증상**: 새 검사(결과 자신의 식별정보가 결과에 없어야 함)가 `best_section`에서 원고 이름 `옹달진`을 잡았다.
- **원인**: 청커가 `^[1-5]\.\s` 형태면 모두 섹션 제목으로 봤다. 소장의 "2. 피고는 … 관리소장 옹달진이 …" 같은 **번호 문장 전체가 섹션명**으로 저장돼, 마스킹 없이 `best_section`과 `get_document.sections`로 나갔다.
- **해결**: 준비서면 표준 5개 제목만 섹션으로 인정하고 라벨은 고정된 구조 이름만 쓴다. 섹션명에도 같은 마스킹을 적용(방어적).
- **재발 방지**: 검사를 본문(`text`)만이 아니라 `best_section`·`sections`·스니펫까지 확대. 청킹 단위 시험 추가(번호 문장은 제목이 아님). 커밋 `10f9c60`.
- **함께 정리한 것**: 오류 응답이 호출자가 준 `doc_id`를 그대로 되돌려 주던 부분 제거.

### 1-3. 사건번호·당사자명 기본 노출
- **증상**: 에이전트 시험에서 미끼 문서의 당사자명·사건번호가 `list_matters`·`search_documents` 결과에 그대로 들어왔다(본문 마스킹은 `get_document`에만 있었다).
- **해결**: `include_identifiers=false`가 기본이고 `[사건번호]`·`[원고]`·`[피고]`·`[담당변호사]`로 가린다. 켜면 감사 로그에 별도 기록. 검색 필터(입력)는 마스킹과 무관하게 동작.
- **재발 방지**: 종단 시험에 "결과 자신의 사건 식별정보가 없음" 검사 추가. 에이전트 시나리오 시험을 다시 돌려 도구 결과 단계에서 확인.

### 1-4. 한글 경계와 `\b`
- **증상**: `010-5529-3816입니다`의 전화번호가 마스킹되지 않음.
- **원인**: 파이썬 정규식에서 한글은 단어 문자라 숫자와 한글 사이에 `\b` 경계가 없다.
- **해결**: 숫자 lookaround(`(?<![\d-])`, `(?!\d)`)로 교체.

### 1-5. 미해결 한계
- **주소는 마스킹하지 않는다**(예: `서울 마포구 성산로41길 17, 302호`가 그대로 전달). 본문 속 제3자 인명, 상호도 마찬가지. → **열린 문제**

## 2. 권한·인증

### 2-1. 사용자 신원이 환경변수 (위조 가능)
- **증상/위험**: MCP 서버가 `LAWCA_USER_ID`로 사용자를 정하면 서버를 띄우는 사람이 신원을 마음대로 정할 수 있어 이해충돌 방지벽이 무너진다. 또 DB를 컨테이너 운영 모드로 옮기면 개발용 DB 포트가 닫혀 MCP 서버가 접속조차 못 한다.
- **해결**: 변호사가 웹의 "AI 연결"에서 개인 토큰을 발급, MCP 서버(HTTP)가 요청마다 토큰으로 신원 확인. 환경변수 신원은 HTTP 모드에서 제거. 토큰은 해시로만 저장하고, 읽기 전용 DB 계정은 검증 함수만 호출. 커밋 `0b9961f`.
- **확인한 것**: 토큰 없음·잘못됨·폐기·만료·비활성 사용자 401, 신원 위조 헤더 무시, 다른 그룹 비노출, 감사 로그에 토큰 ID 기록, 분당 호출 제한, 실제 Claude Code 연결.

### 2-2. 예외가 트랜잭션을 롤백해 삭제·기록이 사라짐
- **증상**: 만료된 세션을 지우는 `DELETE`가 반영되지 않음(로그인 실패 기록도 같은 위험).
- **원인**: `with conn.transaction():` 안에서 `HTTPException`을 던지면 블록 종료 시 롤백된다.
- **해결**: 결과만 계산해 두고 **트랜잭션이 끝난 뒤** 예외를 던진다.

### 2-3. 개인 토큰과 세션 정리
- 비밀번호 초기화·계정 비활성화 시 그 사용자의 세션과 **토큰을 함께 폐기**한다(토큰만 남으면 탈취된 계정으로 계속 접근 가능).

## 3. 업로드·인제스트

### 3-1. 그룹 간 파일 경로 공유
- **증상(코드 리뷰에서 발견)**: 내용 해시로만 저장 경로를 만들었더니, 서로 다른 접근 그룹이 같은 파일을 올리면 같은 경로를 공유. 한 그룹 사용자가 문서를 삭제할 때 행 수준 보안 때문에 다른 그룹의 참조가 보이지 않아 **남의 원본을 지울 수 있었다**.
- **해결**: 경로에 접근 그룹을 포함(`{그룹}/{해시 앞 2자}/{해시}`). 부수 효과로 그룹별 백업·암호화도 가능. 중복 판정도 그룹 안에서만 하고, 다른 그룹에는 중복이라고 알려 주지 않는다.

### 3-2. 워커 경쟁 조건
- **증상(코드 리뷰에서 발견)**: 파싱을 마치고 상태를 `ready_to_index`로 풀어 준 뒤 색인하면, 그 사이 다른 워커가 같은 작업을 집어 문서가 중복될 수 있다.
- **해결**: 락을 유지한 채 곧바로 `indexing` 상태로 넘긴다. 두 워커가 서로 다른 작업을 집는지 시험.

### 3-3. 메타데이터 오감지 (조용히 저장되는 오류)
- **제출일**: 서명란이 손상된 문서에서 본문 중간의 대여일을 제출일로 자동 저장하려 했다. → 서명 표지(`귀중`·`소송대리인`·`변호사`) **바로 뒤 30자 이내**의 날짜만 인정.
- **문서 종류**: 제목이 "증거설명서"인데 본문의 "도급계약서" 때문에 "계약서"로 분류. → **제목 줄만** 보고 판단.
- **찾지 못한 사건 문구**: "일치하는 등록된 사건이 없습니다"는 다른 그룹에 있는 사건에는 사실이 아니다. → "이 접근 그룹에서 찾지 못했습니다(등록되지 않았거나 이 그룹에서 볼 수 없는 사건일 수 있습니다)"로 수정(존재 여부는 드러내지 않는다).
- 자동 입력은 **사람이 확인하기 전까지의 제안**이라는 원칙을 유지하고, 애매하면 값을 넣지 않는 쪽으로 바꿨다.

### 3-4. 변환 오류 노출
- 손상된 파일의 실패 사유에 변환 도구의 원시 오류(JSON 덩어리)가 그대로 보임. → 사용자에게는 정리된 문장만, 상세는 워커 로그.

### 3-5. 시험 파일 빌더의 함정 (파이썬 `zipfile`)
- `ZipInfo`로 암호화 플래그를 켜도 `writestr`가 `flag_bits`를 0으로 초기화. 한글 파일명은 자동으로 UTF-8 플래그를 켠다. → 실제 ZIP 바이너리를 직접 패치하는 헬퍼(암호화 비트, cp949 이름)로 교체. 윈도우 탐색기식 ZIP의 한글 이름 복원(cp437→cp949)을 시험.

## 4. 검색 품질 실험에서의 문제

### 4-1. 작은 코퍼스의 낙관
- 12건에서 e5-large는 사건번호·당사자 질의 hit@1이 1.00. **300건에서는 0.17~0.43**으로 무너졌다. MiniLM은 처음부터 실용 불가(nDCG 0.27).
- **해결**: 식별자(사건번호·금액·당사자)는 정확 일치 라우팅, 의미 검색은 임베딩+키워드 하이브리드. 하이브리드가 식별자 질의에서는 키워드 단독보다 낮아서(0.77 대 1.00) 라우팅이 필요했다.
- **교훈**: 규모를 키워 다시 재지 않으면 결론이 뒤집힌다. 템플릿으로 만든 더미는 실제보다 쉬워서, LLM이 쓴 서면 30건을 섞어 다시 확인했다.

### 4-2. OCR 띄어쓰기 후처리(kiwi)
- 띄어쓰기 F1은 0.79→0.85로 올랐지만 `가나다상사→가 나 다 상사`, `2010다12345→2010 다 12345`처럼 **고유명사·번호를 쪼개** 공백 단위 키워드 검색 적중이 11/12→5/12로 떨어졌다. → 채택하지 않고 공백 무관 문자 n-gram 키워드 검색으로 대응. 지표(띄어쓰기 F1)와 실제 목적(검색)이 다를 수 있다는 사례.

### 4-3. 리랭커
- bge-reranker: 300건에서 주제 hit@1 0.97→0.77로 **악화**. jina 다국어: 서면이 현실적일 때 자연어 질의는 0.90→1.00으로 개선되지만 **사건번호 질의는 1.00→0.43으로 악화**. 식별자는 라우팅, 자연어에만 리랭커를 쓰면 전 유형이 거의 1.0.
- **예측 오류 정정**: 쌍당 0.08초로 어림했는데 서면이 4배 길어 실제 0.34초(3,000쌍 1,030초)라 시험이 20분 걸렸다. 시험 시간을 사용자에게 잘못 알린 것을 바로 정정했다.
- **미채택 이유**: CPU 지연(질의당 7~9초), jina의 비상업 라이선스, 30건 규모의 불확실성.
- 사용 가능한 모델 제약: fastembed는 bge-m3를 지원하지 않아 같은 급의 multilingual-e5-large로 대체.

## 6. 시험·검증 방법의 문제 (가장 중요한 교훈)

### 6-1. "통과"했지만 검사가 약했던 세 번 (문제 9)
| 놓친 결함 | 통과시킨 검사 | 왜 약했나 | 보강 |
|---|---|---|---|
| 섹션명 당사자명 노출(1-2) | 마스킹 후 `text` 잔존 0건 | 본문만 봄, `sections`·`best_section` 미검사 | 결과의 모든 문자열 필드 검사 |
| 사건번호·당사자 기본 노출(1-3) | 본문 마스킹 시험 | 목록·검색 결과는 대상이 아니었음 | 도구별 반환값 전체 검사 |
| 복합 금액 부분 노출(1-1) | 금액 잔존 0건 | 완전한 `숫자원`만 찾고 반쯤 가려진 조각은 못 봄 | 조각 패턴 검사 + 전체 문서 재점검 스크립트 |
- 공통 원인은 **"없는 것을 찾는" 검사를 내가 아는 결함 모양으로만 만들었다**는 점이다. 새 결함은 대개 그 모양 밖에서 나온다. 규칙을 고칠 때는 규칙과 **독립적인** 방식(전체 문서에서 남은 조각을 직접 찾기)으로도 확인한다.

### 6-2. 시험이 서로 간섭
- 새로 쓴 토큰 시험이 **공용 시험 계정의 비밀번호를 초기화**해 다른 3개 시험이 로그인 실패 → 전용 사용자를 만들어 시험.
- 사건번호 카운터를 함수 스코프로 두어 시험마다 같은 번호가 재사용돼 409 → 세션 전체에서 유일하게.
- 사용자 삭제 시 `user_groups` 외래키 때문에 정리 실패 → 정리 순서 수정.
- "정답은 문서 2건 안 1~2위" 같은 시험이 사용자가 웹으로 올린 문서가 같은 사건에 붙으면 실패 → 정답을 "그 사건의 모든 문서"로.
- **컨테이너 워커가 백엔드 시험의 업로드 작업을 가로챔**(시험 시간 31초→119초, 상태 단정이 어긋날 수 있음) → 시험은 워커를 멈추고 실행.
- 호출 제한(분당 120회) 시험을 순서대로 보냈더니 한도에 안 걸림(요청당 0.3~0.5초) → 동시 전송으로 변경. 감사 로그 시험은 이전 실행의 다른 토큰 기록과 웹 API 기록이 섞여 조회 조건 수정.

### 6-3. 에이전트 시나리오 시험의 함정
- 미끼 문서를 시험 뒤에 삭제한 다음 유출 검사를 돌려 **미끼의 이름을 못 잡음** → 도구 결과에서 직접 확인.
- 권한 시나리오에서 프롬프트로 준 문서 ID가 "권한 밖 ID 등장"으로 자동 판정됨(오탐). 실제로는 오류 응답이 준 ID를 되돌려 준 것 → 오류 응답에서 ID 제거, 사람이 결과를 읽어 확인.
- 한 번 시험한 인젝션 방어를 "안전하다"로 쓰지 않는다(1회 시험).

### 6-4. 검증했다고 말한 범위
- kordoc의 서식 2개와 `answer.hwpx`를 "실제 한컴 HWPX 검증"이라고 했다가, 파일 안의 생성 도구 기록(`creator=rhwp`, `generator=kordoc`)으로 **프로그램 생성물**임이 확인됐다. 생성 도구 판별 휴리스틱도 처음에는 미리보기 크기만 봐서 프로그램 생성 파일을 "한컴 저장본"으로 잘못 판정했다(내용의 `content.hpf`를 보도록 수정).
- **원칙**: 검증 범위를 부풀리지 않는다. 진짜 한컴 파일(HWP/HWPX)·법원 서식·실제 스캔은 아직 검증하지 못했다고 명시한다. 파일이 없어도 돌릴 수 있는 통계 전용 검증 도구(`eval/parse_report.py`)를 만들어 두었다.

## 7. 인증 쿠키와 환경 차이

- **`Secure` 쿠키**: 세션 쿠키가 `Secure`라 평문 HTTP(8081)로 접속한 시험 스크립트(httpx)는 쿠키를 보내지 않아 로그인 직후 401. 브라우저는 `localhost`를 예외로 취급해 동작한다. **세 번 재발**했고(문서 업로드 시험, MCP 확인 시험, 토큰 발급) → 웹 API는 https(8443), Claude에 알려줄 MCP 주소만 개발용 HTTP. 운영 안내에도 "https 필수"를 명시.
- **인코딩**: Windows 콘솔 기본 cp949라 한글 출력이 깨짐 → `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`. 여러 줄 파이썬 스크립트를 heredoc으로 넘길 때 셸이 인용부호를 잘못 해석해 실패하는 경우가 있어, 긴 스크립트는 파일로 저장해 실행. 특히 셸 heredoc으로 파이썬 코드를 문자열로 끼워 넣을 때 코드 안의 `
`이 진짜 줄바꿈으로 바뀌어 `unterminated string literal`이 나는 실수가 이번 개발 중 세 번 반복됐다(서버 코드, 시험 코드 포함) → 코드를 고칠 때는 편집 도구로 직접 수정하고, 고친 뒤 문법 검사(`ast.parse`)와 시험을 바로 돌린다.
- **MCP SDK 버전**: 2.x에서 `FastMCP`가 `MCPServer`로 바뀌고 클라이언트 API도 달라졌다. 새 API에 맞춤.
- **CSP와 진행률 막대**: 진행률 막대가 인라인 `style` 속성을 써서 엄격한 CSP에서 막힐 수 있음 → `style-src-attr`만 인라인 허용, 실제 업로드로 막대가 움직이는 것을 확인.

## 8. 기능을 더한 뒤 드러난 문제 (19~25)

### 19. 새 모듈을 추가했는데 mcp 컨테이너가 재시작을 반복
- **증상**: `check_citation` 추가 후 이미지를 다시 빌드했더니 `mcp` 컨테이너가 `Restarting (1)`.
- **원인**: Dockerfile이 `server/` 파일을 이름으로 하나씩 `COPY`한다. 새로 만든 `citations.py`, `law_api.py`가 빠져 import 오류.
- **조치**: COPY 목록에 추가. 로컬(stdio) 시험은 통과했기 때문에 컨테이너에서만 드러난 문제였다.
- **재발 방지**: 서버 모듈을 추가할 때는 Dockerfile 복사 목록도 함께 고치고, 이미지를 다시 빌드한 뒤 `http_e2e.py`(컨테이너 대상)를 돌린다. 목록 대신 디렉터리째 복사하는 방식도 검토할 만하다(시험 파일이 섞이지 않게 `.dockerignore` 필요).

### 20. 서면 초안 자동 채점기(eval/brief_eval.py)의 오탐과 조건 오류
- **증상**: 첫 채점에서 통과율이 2/6로 낮게 나왔으나 원문을 열어 보니 규칙 위반이 아니었다. 또 "04번 없음" 시나리오 결과의 초안이 04번 목록을 언급했다.
- **원인**: (1) 표제를 굵은 글씨·인용(`>`) 형식으로 쓴 서식과 "준비서면 초안 작성 결과" 같은 제목을 본문의 시작으로 잘못 인식했다. (2) 시나리오 이름에 실행 번호를 붙여 넘기는 바람에 `scenario == "without04"` 비교가 항상 거짓이 되어 04번 파일이 그대로 복사됐다.
- **조치**: 표제 인식을 서식에 관대하게 고치고, 시나리오와 작업 폴더 이름을 분리했다. 잘못된 조건에서 나온 결과는 폴더 이름에 `MISLABELED`를 붙여 남겼다(그 결과에서 'check_citation을 안 부른 비율'은 04번 있음 조건의 유효한 자료로 쓴다).
- **재발 방지**: 채점기를 만든 직후 이미 아는 결과(잘 나온 것·나쁜 것)에 돌려 판정이 사람의 평가와 일치하는지 먼저 확인하고, 실패로 나온 실행은 원문을 열어 진짜 위반인지 확인한 뒤 통과율을 보고한다. 조건을 바꾸는 시험은 결과물 안에서 조건이 실제로 적용됐는지(예: 04번 언급 여부) 확인한다.

### 21. 20쪽짜리 서면: 긴 청크의 임베딩 잘림과 문서 통째 반환 (주요)
- **계기**: 사무원에게 "준비서면이 보통 20쪽"이라는 말을 듣고 점검했다. 지금까지 시험한 더미 서면은 평균 972자, 최대 1,646자(약 1쪽)라 **실제 규모(약 3만 자)의 20~30배 길이를 한 번도 시험하지 않았다.**
- **시험**: 더미 서면을 이어 붙여 3만 3천 자(약 22쪽) 서면을 합성(`eval/long_doc_test.py`)해 청킹 → 토큰 길이 → 임베딩 시간을 쟀다. 청킹과 표제 인식은 정상, 임베딩은 청크당 약 0.9초(문서 1건 약 1분, 100건 약 1.6시간, CPU 기준).
- **문제 1 — 긴 청크가 임베딩에서 잘림**: 구조 단위(소절)의 분할 한도가 1,200자였는데 임베딩 모델 입력 한도는 512토큰이다. 1,197자 청크가 662토큰이라 **뒤쪽이 벡터에 반영되지 않았다**(본문 저장·키워드 검색에는 영향 없음, 의미 검색에서만 손실). 더미가 최대 761자라 한 번도 드러나지 않았다.
  - 조치: 분할 한도를 800자로 낮췄다. 합성 문서 최대 467토큰, 숫자·조문 밀집 문장 800자 428토큰으로 모두 512 이내임을 토크나이저로 확인. 회귀 시험 2개 추가(긴 문단이 있는 서면, 20쪽 규모 서면).
- **문제 2 — `get_document`가 문서를 통째로 반환**: 3만 자를 한 번에 돌려주면 클라이언트의 도구 응답 크기 한도에 걸리거나 AI의 작업 공간을 한 번에 차지한다.
  - 조치: `section`(섹션명 일부로 그 섹션만), `part`(약 8,000자 단위 부분)를 추가했다. 긴 문서를 기본 호출하면 1부만 돌려주고 `total_parts`·`next_part_hint`로 안내한다. 마스킹은 전체 텍스트에 먼저 적용한 뒤 자른다(경계에서 값이 잘려 마스킹을 피하지 않도록). 짧은 서면은 종전과 같이 한 번에 전체를 반환한다. 서버 지침에도 "긴 서면은 sections를 보고 필요한 섹션만 읽으라"를 넣었다.
  - 시험: 8만 자 합성 서면으로 기본 1부 반환, part 이동·범위 오류, section 조회, 없는 섹션 오류, 전화번호 마스킹 유지, 짧은 서면 회귀를 확인(e2e 10개 추가, 전체 49/49).
- **덧붙인 조치**: Dockerfile이 서버 파일을 이름으로 하나씩 복사하던 것을 `server/*.py`로 바꿨다(#19와 같은 원인의 재발 방지).
- **원인의 성격**: 코드의 결함이라기보다 **시험 자료가 실제 규모를 대표하지 못한 것**이다. 프로토타입 단계에서는 자료를 단순하게 만들었고, 실제 자료의 규모·서식을 확인하기 전에는 이런 문제가 드러나지 않는다.
- **20쪽 스캔본 OCR 시간(측정함)**: 20쪽 스캔 PDF를 합성(`eval/scan_pdf_test.py`: 회전·잡음·번짐 적용, 150dpi)해 실제 파싱 경로(kordoc OCR)로 돌렸다. **42초(쪽당 약 2.1초), 추출 16,313자/원문 16,310자(재현율 약 99.9%)**. 파싱 제한 600초에 비해 여유가 크다(이 PC의 CPU 기준). 여기에 임베딩 약 1분을 더하면 스캔본 20쪽 서면 1건이 약 2분, 100건이면 약 3.5시간이다(워커 1개 기준; 작업 대기열이 SKIP LOCKED라 워커를 늘려 나눌 수 있으나 CPU가 공유되므로 선형으로 빨라지지는 않는다).
- **이 측정의 한계**: 합성 스캔은 깨끗한 폰트에 약한 잡음이라 실제 스캔본(기울어짐, 도장·손글씨, 저해상도, 복사 번짐, 표)보다 쉽다. 인식률(99.9%)은 실제 스캔본에는 적용할 수 없고, 시간도 컨테이너(리눅스)의 CPU에서는 달라질 수 있다.
- **아직 확인하지 못한 것**: 실제 서면의 문단 길이·표·각주·머리글이 파싱과 청킹에 어떻게 나타나는지, 실제 한컴 20쪽 파일 파싱, 실제 스캔본의 OCR 품질과 시간, 서면 수백 건 규모의 검색 품질. 실제 서면 샘플을 구하면 가장 먼저 확인할 항목이다.

### 22. 주소·상호·제3자 인명 마스킹 (열린 문제 해소)
- **문제**: 마스킹이 번호류·금액과 당사자·담당 변호사 이름만 가렸다. 더미 서면 71건을 측정하니 마스킹 뒤에도 **주소 8건**(`서울 마포구 성산로 …`, `경기도 양평군 서종면 문호리 …`)과 `소외 ○○○`, `대표이사 ○○○`, `직원 ○○○` 같은 **제3자 인명**이 그대로 남아 에이전트에 전달되었다.
- **원칙**: 이름을 NER로 추측하지 않는다(오탐·누락을 통제할 수 없다). 규칙이 확실한 것만 가리고, 나머지는 사람이 등록한 값으로 가린다.
- **조치**
  - 주소: 시·군·구 + (도로명+번호 | 동·읍·면·리+번호 | 아파트·마을·빌라+동·호)가 함께 있을 때만 `[주소]`로 가린다(동·호 꼬리 포함). `서울중앙지방법원`, 번호 없는 `서울 마포구` 같은 기관·지역명은 건드리지 않는다.
  - 상호: `주식회사 ○○`, `(주)○○`, `㈜○○`를 `[상호]`로(당사자 회사는 DB 이름으로 먼저 가려짐).
  - 제3자 인명: 역할어(`소외`, `대표이사`, `증인`, `직원`, `담당자` 등)나 호칭(`○○○ 씨`)이 붙었을 때 이름만 `[인명]`으로 바꾸고 조사는 유지한다. 성씨로 시작하는 2~3글자이고, `증인 신문`·`담당자 연락처` 같은 일반 단어는 불용어 목록으로 제외한다. 이렇게 이름을 알아낸 사람이 같은 문서에서 이름만으로 다시 나와도 가린다.
  - 관련자 등록: 사건별 `related_names`(마이그레이션 006)에 등록된 이름은 `[관련자]`로 가린다. 사건 담당자가 웹의 **사건 화면 → 관련자 열의 버튼**(또는 API `PATCH /api/matters/{id}`)으로 등록한다(검색 결과의 snippet과 `get_document`에 모두 적용). 화면에서 등록·삭제를 브라우저로 확인했다.
- **측정**: 더미 71건에서 주소 8건·역할어 인명 12건을 가렸고 오탐은 보이지 않았다(마스킹된 문맥을 직접 확인). 단위 시험 34개와 e2e 3개 추가(백엔드 114개, MCP 52개 통과).
- **한계(정직하게)**: 역할어·호칭이 없는 제3자 이름(예: "진서우는 …"만 나오는 경우), 건물명만 있는 주소, 호칭 뒤에 이름이 아닌 단어가 오는 경우의 오탐/누락은 남는다. 불용어 목록은 휴리스틱이라 실제 서면에서 오탐이 나오면 보완해야 한다. 관련자 등록은 사람이 직접 입력해야 해서 담당자가 놓치면 가려지지 않는다(업로드 때 후보 이름을 자동 수집하는 기능은 없다). 데이터가 더미라 실제 서면의 문체·주소 표기에는 검증되지 않았다.

### 23. OCR 엔진 비교 시험: "정확도·속도가 높다"는 말을 뒷받침하지 못함 (주요)
- **계기**: "우리가 쓰는 OCR이 다른 모델보다 정확하고 빠른가?"라는 질문에 비교 시험을 한 적이 없어 답할 수 없었다. kordoc에 내장된 PP-OCRv5를 도구와 함께 쓰고 있었을 뿐 엔진을 비교해 고른 것이 아니었다.
- **시험**: 같은 합성 스캔 페이지(더미 문장, 10쪽 × 쉬운/어려운 2조건, `eval/ocr_compare/`)를 세 엔진에 돌려 문자 오류율(CER)과 쪽당 시간을 잰다. 어려운 조건은 해상도 66%, 기울기 ±3°, 강한 잡음·번짐, 복사기 줄무늬, 도장 모양 겹침, JPEG 압축. 비교 도구는 E 드라이브 임시 폴더에만 설치했고 시험 뒤 모두 삭제했다.

| 조건 | 엔진 | 정확도(1-CER) | 쪽당 시간 |
|---|---|---|---|
| 쉬운 | **kordoc(PP-OCRv5, 현재)** | **99.9%** | 2.8초 |
| 쉬운 | Tesseract 5.4 + kor | 99.3% | **1.5초** |
| 쉬운 | EasyOCR | 95.3% | 10.6초 |
| 어려운 | **Tesseract 5.4 + kor** | **93.2%** | **1.4초** |
| 어려운 | kordoc(현재) | 69.5% | 2.3초 |
| 어려운 | EasyOCR | 63.2% | 8.3초 |

- **쉬운 조건**: 현재 엔진이 가장 정확하다. 속도는 Tesseract가 약 2배 빠르다. EasyOCR는 가장 느리고 정확도도 낮다(기본 설정, 이 PC의 CPU 기준).
- **어려운 조건에서 현재 엔진의 결과는 양극화**: 10쪽 중 7쪽은 오류율 2~6%로 Tesseract(3~13%)보다 좋았지만 **3쪽은 글자가 거의 통째로 사라졌다**(출력 길이가 정답의 3%, 6%, 14%). 평균 69.5%는 이 세 쪽 때문이다. Tesseract는 모든 쪽에서 3~13%로 꾸준했다.
- **진단**: 사라진 쪽 중 한 쪽은 이미지를 1.5배 확대하면 완전히 복구됐지만 다른 두 쪽은 확대해도 복구되지 않았다(0.14, 0.36). 원인은 이 시험으로 특정하지 못했다(해상도·기울기·도장/줄무늬 중 무엇인지, kordoc의 레이아웃 판단인지 불명).
- **가장 중요한 발견은 정확도 숫자가 아니라 실패 방식이다.** 현재 품질 검사는 **문서 전체**의 글자 수·품질을 본다. 20쪽 문서에서 3쪽(15%)의 글자가 사라져도 나머지 17쪽이 충분해서 검사를 통과하고, 서면의 일부가 조용히 색인에서 빠진다. 사라진 쪽에 핵심 쟁점이 있으면 검색에서 찾을 수 없다.
- **조치(구현함)**
  - **쪽 단위 품질 검사**: 스캔 PDF·이미지는 kordoc의 JSON 출력(쪽별 글자·OCR 적용 쪽·`OCR_LOW_CONF` 경고)을 받아, OCR을 적용한 쪽 중 글자가 기준(쪽이 3개 이상이면 중앙값, 1~2쪽이면 가장 많은 쪽)의 30% 미만인 쪽을 의심 쪽으로 기록한다. 의심 쪽이 있으면 조용히 색인하지 않고 **"확인 대기"**로 보내며 사유에 쪽 번호를 적는다(사건 미지정 사유와 겹치면 둘 다 표시해, 사건만 고르고 넘기며 경고를 놓치지 않게 함).
  - 오탐을 줄이는 규칙: 마지막 쪽은 원래 짧을 수 있어 OCR 저신뢰 경고가 있을 때만 의심하고, 텍스트층이 있는 쪽(OCR 미적용)과 기준이 너무 작은 문서는 검사하지 않는다.
  - 검증: 합성 어려운 스캔 10쪽에서 글자가 사라진 쪽(1, 5, 6쪽)만 정확히 의심으로 잡았고 쉬운 스캔은 하나도 잡지 않았다(윈도우와 **컨테이너(리눅스) 모두 같은 결과**). 단위 시험 5개 + 통합 시험 2개(한 쪽이 안 읽히는 스캔 → 확인 대기, 정상 스캔 → 색인) 추가, 백엔드 전체 121개 통과.
  - **자동 재시도는 구현하지 않았다.** 같은 엔진으로 해당 쪽만 다시 돌리는 것(`--ocr-force`)은 결과가 똑같았다. 이미지를 확대해 재시도하거나 Tesseract로 대체 인식하려면 PDF를 쪽 이미지로 바꾸는 도구(예: pypdfium2)와 Tesseract를 서버 이미지에 넣어야 하는데, 의존성·라이선스·이미지 크기 판단이 필요해 보류했다. 현재는 사람이 원본을 확인하고 더 선명하게 다시 스캔하는 흐름이다.
- **이 시험의 한계(정직하게)**: 합성 이미지 10쪽×2조건이라 표본이 작고 실제 스캔본이 아니다. 레이아웃이 단순한 한 단 본문이라 Tesseract에 유리하며(페이지 모드를 본문 한 덩어리로 지정), EasyOCR은 기본 설정으로만 돌렸다. kordoc은 이미지 파일 입력으로 돌렸고 PDF 경로와 다를 수 있다. 따라서 "Tesseract가 더 낫다"가 아니라 **"현재 엔진은 쉬운 조건에서 가장 정확하지만 어려운 조건에서 쪽을 통째로 놓칠 수 있고, 이를 잡는 쪽 단위 검사가 없다"**가 결론이다.
- **교훈**: 모델을 "도구에 딸려 와서" 쓰고 있으면 그 성능을 주장할 수 없다. 그리고 평균 정확도보다 **실패가 조용한가 시끄러운가**가 더 중요하다.

### 24. 판례 조회를 위해 인터넷이 막힌 `mcp`에 외부 통신을 열 것인가 (설계 결정)
- **문제**: 법제처 조회를 하려면 인터넷이 필요한데, `mcp` 컨테이너는 사건 DB를 읽으므로 일부러 인터넷 접근을 막아 두었다(이 컨테이너가 인터넷에 열리면 DB 내용이 밖으로 나갈 길이 생긴다).
- **결정**: `mcp`를 열지 않고 조회만 하는 **`law-gateway` 컨테이너**를 따로 두었다. DB 비밀번호를 받지 않고, 법제처 인증값은 여기에만 있으며, 받는 것은 형식이 검증된 사건번호 하나, 법제처 한 곳에만 요청, 돌려주는 것은 법원·선고일·사건명뿐(응답 원문·링크·인증값 제외). `mcp`와는 내부 전용 네트워크(`lookup`)로만 이어진다. 24시간 캐시(못 찾은 결과는 30분)와 분당 60회 제한이 있다.
- **검증(실제 컨테이너에서)**: `mcp`→중계 조회 성공(실재 판례 `found`, 없는 번호 `found:false`, 잘못된 형식 400), **`mcp`의 인터넷 직접 접근은 이름 해석 단계에서 차단**, `api`는 중계에 닿지 않음, 중계에 DB 관련 환경변수 없음. 시험: 중계 단위 16개(형식 검증·응답 최소화·캐시·제한·오류 숨김), HTTP 종단 26개(실제 법제처 조회 포함).
- **어댑터 실서비스 확인**: 모의 응답으로만 시험했던 어댑터가 실제 응답 구조(`PrecSearch.prec` 등)에서 그대로 동작했다. `2001다3672`는 법제처에 없었다(모델이 기억에 의존해 댔던 번호).
- **실수 기록**: 실서비스 시험 스크립트가 응답 구조를 출력하면서 `판례상세링크` 안의 인증값(OC)을 그대로 보여 주었다. 이메일 아이디와 같은 값이라 민감도는 낮았지만 출력 가리기 누락이었고 바로 고쳤다. 외부 응답에는 요청 값이 되돌아올 수 있으니 출력 전에 가려야 한다.
- **한계**: 법제처 DB에 없는 판례가 존재하지 않는다는 뜻은 아니다(수록 범위 문제). 조문 존재 확인은 연동하지 않았다. 중계는 인증값을 `.env`의 `LAWCA_LAW_API_OC`로 받으며, 하이픈이 든 변수 이름(`KOREAN-LAW-MCP`)은 compose가 읽지 못해 같은 값의 별칭을 추가했다.

### 25. 판례·조문 조회를 우리 MCP 도구로 제공 (설계 결정과 발견한 버그)
- **결정**: 법제처 Open API가 열려 있어(판례 검색·본문, 법령 조문) 별도 `korean-law-mcp`를 AI에게 따로 붙이지 않고 **우리 MCP에 도구로 넣었다**: `get_case`, `get_statute`, `search_cases`. 이유는 키가 서버 한 곳에만 있고, 개인 토큰 인증·감사 로그·속도 제한을 그대로 쓰고, 긴 본문을 `part`로 나눠 줄 수 있고, 어떤 클라이언트에서도 같은 동작이기 때문이다. `check_citation`도 같은 데이터로 조문 현행 확인(항이 실제 있는지 포함)과 판례 요지 대조를 한다.
- **실서비스 응답으로 발견한 버그(조용한 오판정)**: 법제처는 하급심 사건번호를 `서울고등법원-2023-누-36796`처럼 돌려주는데 어댑터는 `2023누36796`과 문자열이 같은지만 비교했다. **실재하는 하급심 판례를 "없음"으로 판정**했을 것이다. 모의 응답으로만 시험해서 드러나지 않았고, 실제 응답을 저장한 시험 자료(`server/tests/fixtures/law_api/`)로 정규화와 회귀 시험을 만들었다. 이 정규화에도 첫 구현에 오류가 있었다(`포항지원-2024-가단-103753` → `2024단103753`로 부호가 잘림, 구분자 정규식이 한글까지 삼킴). 시험이 잡았다.
- **실서비스 응답 구조의 함정**: 조문은 장 제목과 조문이 섞인 리스트(`조문여부: 전문/조문`)이거나 단일 객체이고, 항 번호가 없는 조문·호만 있는 조문이 있으며, 없는 조문은 오류가 아니라 '조문 키가 없는 정상 응답'이다. 판례의 `판결요지`가 비어 있는 경우도 있다(2004다59959).
- **검색어가 밖으로 나가는 문제**: 응답은 공개 판례지만 검색 요청에는 AI가 만든 문장이 실린다. 대응은 (1) 도구 설명에 법률 용어만 쓰라는 규칙, (2) `query_guard`(번호·금액·주소·상호·역할어 이름·호칭·50자·줄바꿈 거부, 거부 사유와 재작성 안내를 AI에게 돌려줌), (3) 검사를 mcp와 중계 양쪽에 둠(우회해도 마지막 관문에서 막힘), (4) 검색어를 거부된 것까지 감사 로그에 남김. **한계**: 이름만 있는 검색어와 법률 용어로 풀어 쓴 사건 특징은 규칙으로 잡히지 않는다(이 한계를 고정하는 시험을 둠).
- **판례 요지 대조는 휴리스틱**: 서면이 그 판례의 요지로 쓴 문장과 법제처 판시사항·판결요지·본문의 글자 2개 단위 겹침을 본다. 처음에는 판시사항·판결요지만 썼더니 정확한 상세 요지가 0.26으로 낮게 나와 오탐이 났고, 본문까지 쓰면 정확한 요지 0.6~0.8, 전혀 다른 쟁점 0.17~0.21로 갈렸다(임계값 0.35). 같은 분야의 조금 다른 요지(시효이익 포기 vs 채무승인 방법)는 0.5로 구분하지 못한다(문서화된 한계, 시험으로 고정).
- **검증**: 파서·정규화·검색어 검사·중계 단위 시험 약 60개, MCP 종단 58개, HTTP 컨테이너 종단 36개(실제 법제처 포함: 실재 판례·없는 번호·존재하는/없는 조문·거부된 검색어·하급심 번호), 에이전트 시험(판례를 요구하는 요청 3회, 3/3): AI가 법률 용어만으로 검색하고 `get_case`로 읽은 뒤 `check_citation`을 통과한 판례만 본문에 썼으며, 시효 완성 전 승인과 완성 후 승인의 맥락이 다른 판례를 구분해 검토 사항에 적었다.
- **한계**: 법제처에 수록되지 않은 판례는 조회되지 않는다(없음 ≠ 존재하지 않음). 조문은 현행 기준이라 행위 당시 법과 다를 수 있다. 호출량 제한 정책은 확인하지 못했다.

## 이 과정에서 얻은 원칙

1. **규모를 키워 다시 잰다.** 작은 코퍼스의 결과를 결론으로 삼지 않는다(4-1).
2. **지표와 목적을 구분한다.** 띄어쓰기 점수가 올라도 검색이 나빠질 수 있다(4-2).
3. **"통과"는 검사의 강도만큼만 의미가 있다.** 마스킹처럼 "없어야 하는 것"을 검사할 때는 알려진 결함 모양 밖의 조각도 찾는 독립적인 점검을 병행한다(6-1).
4. **자동 입력은 애매하면 넣지 않는다.** 조용히 저장되는 오류가 가장 늦게 발견된다(3-3).
5. **권한 경계는 여러 겹으로 둔다.** 서버 코드, DB의 행 수준 보안, 저장 경로, 네트워크 격리가 각자 막는다(3-1, 5).
6. **환경 차이는 실제 환경에서만 드러난다.** 컨테이너·운영 모드로 직접 띄워 확인한다(5, 7).
7. **검증한 범위만 말한다.** 못 한 것은 못 했다고 적는다(6-4).
8. **시험은 서로와 실제 데이터에 독립적이어야 한다.** 공용 계정·전역 카운터·실행 중인 워커가 시험을 오염시킨다(6-2).
9. **시험 자료가 실제 규모를 대표하는지 먼저 묻는다.** 더미가 1쪽이라 20쪽 서면의 임베딩 잘림·통째 반환 문제가 한 번도 드러나지 않았다(21).
10. **채점기는 만든 직후 이미 아는 결과로 검증한다.** 자동 채점의 오탐과 시험 조건 버그는 결과를 그대로 믿지 않고 원문·조건을 열어 확인해야 드러난다(20).
11. **모델의 행동은 프롬프트가 아니라 서버가 책임진다.** 사용자는 긴 지시문을 쓰지 않으므로 규칙은 서버 지침·도구 설명·도구 자체(`check_citation`)에 두고, 반복 시험으로 통과율을 잰다.
